Theory recap

The ideas behind every table and query, from Weeks 1 to 8. Read the cards, then scroll down for a quick Theory check.

Data models & business rules

Data models

  • A data model is a simple, usually graphical, representation of complex real-world data.
  • Building blocks: entity, attribute, and relationship.
  • Three levels of design: conceptual (high level, the ERD), logical (relational tables), and physical (how it is stored).

Business rules

  • Brief, precise, unambiguous descriptions of an organisation's policies, procedures or principles.
  • They tell us how to design the database, and they come from managers, documents and interviews.
  • Rule of thumb when reading them: nouns become entities, and verbs become relationships.

From a business rule to an ERD

A business rule is not a relationship by itself. When you read the rule, the nouns become entities and the verb becomes the relationship. So one rule gives you both, and the ERD it produces is a data model.

Example business rule: "A publisher publishes many books; each book is published by exactly one publisher."

  • Nouns become entities: Publisher, Book.
  • The verb becomes the relationship: publishes.
  • The wording sets the cardinality: one publisher, many books, so 1:M.

As an ERD (a data model): PUBLISHER (1) links to many BOOK (M) through the relationship 'publishes'. That is exactly our two Lab 7 tables, linked by PublisherID.

Keys & integrity rules

Keys

  • Primary key (PK): uniquely identifies a row; never null.
  • Foreign key (FK): matches a PK in another table; the link between tables.
  • Candidate key: a column that could be the PK. Composite key: two or more columns that are unique together.

Integrity rules

  • Entity integrity: a PK must be unique and not null.
  • Referential integrity: an FK must match an existing PK, or be null.
  • In our tables, Book.PublisherID must equal a real Publisher.PublisherID, or be null (like book B05).

Entity Relationship Diagram (ERD)

Components

  • Entity: a thing we store data about (Publisher, Book).
  • Attribute: a property of an entity (Name, Price).
  • Relationship: how entities connect, described by connectivity and cardinality.
  • Drawn with Crow's foot or Chen notation.

Relationship types

  • 1:1 one to one.
  • 1:M one to many. One publisher has many books, so Publisher to Book is 1:M.
  • M:N many to many. This must be resolved with a bridge (associative) entity.

Normalization process

Normalization corrects table structures to reduce redundancy and avoid anomalies. It works in stages.

UNF
Un-normalised. Has repeating groups and redundancy.
1NF
Remove repeating groups, make every cell a single (atomic) value, and choose a primary key.
2NF
In 1NF and remove partial dependencies (a non-key column depending on only part of a composite key).
3NF
In 2NF and remove transitive dependencies (a non-key column depending on another non-key column).
Why it matters here: splitting Publisher and Book into two tables linked by a key is normalization in action. Each fact is stored once.

Data types

  • nvarchar(50) text
  • decimal(10,2) prices
  • date dates (YYYY-MM-DD)
  • integer whole numbers

Retrieve & filter

SELECT Name, Price FROM Book;
SELECT * FROM Book
WHERE Author = 'K.Vince';
SELECT DISTINCT Address FROM Publisher;
SELECT * FROM Book
WHERE PublishedDate IS NULL;

Operators

  • BETWEEN a AND b range (inclusive)
  • AND / OR combine conditions
  • LIKE 'b%' pattern (% any, _ one)
  • IN (...) match a list
  • ORDER BY col DESC sort

Aggregates & grouping

SELECT COUNT(*) AS TotalBooks
FROM Book;

SELECT Author, COUNT(*) AS Total
FROM Book
GROUP BY Author;

Remember

  • COUNT SUM AVG MIN MAX summarise a column.
  • Use AS to rename the result column.
  • GROUP BY makes one result row per group.

What is a subquery?

A query inside another query, the heart of Lab 7.

The idea

  • A subquery is a SELECT placed inside another query.
  • The inner query runs first; its result feeds the outer query.
  • Use = when the inner query returns ONE value.
  • Use IN when it can return SEVERAL values.
  • A subquery can also drive an UPDATE.
-- Q4: books published by 'Deitel'
SELECT * FROM Book
WHERE PublisherID =
  (SELECT PublisherID FROM Publisher
   WHERE Name = 'Deitel');

Inner query finds Deitel's ID (P02), then the outer query lists that publisher's books.

Why a subquery, and not just 'P02'?

A fair question: why write a second query to fetch P02 instead of just typing WHERE PublisherID = 'P02'?

People know names, the database knows codes

  • We recognise the publisher by its name, 'Deitel'. The database links the tables by a short internal code, PublisherID 'P02', which nobody memorises.
  • The subquery looks up the code from the name you actually know. You ask in human terms ('Deitel'), and SQL finds the matching ID for you.

Two practical wins

  • No manual lookup. Otherwise you would run one query to discover Deitel is P02, read it, then type 'P02' into a second query. The subquery does both at once.
  • It stays correct. If the IDs are ever reorganised, a hard-coded 'P02' breaks. Looking it up by name always returns the right code.
Real-world picture: on an online bookstore a customer searches 'Deitel', not 'P02'. Behind the scenes the site looks up Deitel's ID and pulls the matching books. That hidden lookup is exactly what the subquery does for you.

Five subquery patterns

Almost every Lab 7 question is one of these shapes.

1. One value, use =

WHERE col = (SELECT col FROM t WHERE ...);

2. Many values, use IN

WHERE col IN (SELECT col FROM t WHERE ...);

3. Aggregate over a subset

SELECT COUNT(*) FROM t
WHERE col = (SELECT ...);

4. Rows with no match

WHERE NOT EXISTS (SELECT 1 ...)
-- or --
WHERE col NOT IN
   (SELECT col FROM t
    WHERE col IS NOT NULL);

5. Groups passing a test

WHERE col IN (SELECT col FROM t GROUP BY col HAVING COUNT(*) > 1);
NULL trap: with NOT IN, if the subquery contains a NULL (Book B05 has a NULL PublisherID) the whole condition returns no rows. Add WHERE PublisherID IS NOT NULL, or use NOT EXISTS.
